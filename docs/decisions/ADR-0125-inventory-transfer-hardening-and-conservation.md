# ADR-0125: InventoryTransfer Hardening — Creation, Conservation, Reservation Safety, Deactivation

## Status
Accepted

## Context
Source audit of `InventoryTransferService` found: (1) no `create()` service method — creation happens ad hoc via raw `InventoryTransfer::create()`/`InventoryTransferItem::create()` in a route closure, bypassing idempotency and header+items atomicity; (2) `stock_items.incoming` is fully dead — declared in `$fillable`/`$casts`/migration with zero readers or writers anywhere; (3) `dispatch()` validates only raw `on_hand`, never subtracting `reserved`/`quarantined`/`damaged` — a transfer can dispatch stock actively held by a Checkout/Order reservation today; (4) no code path checks `InventorySource.status` or `Warehouse.status` in transfer creation, dispatch, or receive; (5) `partially_received` is a real, tested 6th transfer status undocumented in the original migration comment or ADR-0045.

## Decision
1. **Formal `create()`**: new `InventoryTransferServiceInterface::create()` — idempotency-wrapped (`InventoryIdempotencyService`, operation_type `transfer_create`), single transaction creating the `InventoryTransfer` header and all `InventoryTransferItem` rows atomically. Validates: source≠destination, same tenant, source/destination `status='active'`, items belong to the same tenant, `quantity>0`, no duplicate `(product_id, variant_id)` lines, quantity scale ≤4 decimal places. Same-key+same-payload replay returns the same Transfer; same-key+differing-payload fails closed (requires the `inventory_operation_keys` payload-hash enhancement in ADR-0126's companion migration).
2. **State machine, frozen exactly as source-confirmed**: `draft→in_transit` (direct, confirmed live), `draft→requested`/`requested→in_transit` (both legal per the existing `dispatch()` guard, though no current writer sets `requested` — `create()`'s DTO accepts `initial_status ∈ {draft, requested}` as a caller choice, without building new approval-workflow logic around it), `draft/requested→cancelled`, `in_transit→received`, `in_transit→partially_received`, `partially_received→partially_received`, `partially_received→received`. No backward transitions.
3. **Conservation equations**, activating the previously-dead `incoming` column: on dispatch, `source.on_hand -= q; destination.incoming += q` (destination `StockItem` now `firstOrCreate`'d at dispatch time, earlier than today); on receive-good, `destination.incoming -= r; destination.on_hand += r`; on receive-damaged, `destination.incoming -= d; destination.damaged += d`; on receive-quarantine, `destination.incoming -= z; destination.quarantined += z`. Global `Σ(on_hand+incoming+quarantined+damaged)` is conserved across every transition. `incoming` remains excluded from `available_to_sell` (already true in existing code, unchanged). A new `InventoryMovement::VALID_TYPES` entry is added for the dispatch-time incoming-bucket change; damaged/quarantine-at-receipt is new capability (today's `receive()` only supports a single good-quantity increment).
4. **Reservation safety**: `dispatch()` is changed to validate against `getAvailableToSellQuantity()`'s formula (`on_hand - reserved - quarantined - damaged`) instead of raw `on_hand`, under the same `FOR UPDATE` lock already taken. No new `ReservationOwnerType` is introduced — the existing `reserved` column is already authoritative and a row-lock check at dispatch time is sufficient, mirroring the pattern already proven safe for reservation-vs-reservation races.
5. **Deactivation semantics**: new transfer creation requires both source and destination `InventorySource.status='active'` and, if `Warehouse`-linked, parent `Warehouse.status='active'` (closing a gap — Warehouse.status was never checked anywhere, not even in reservations). Dispatch re-checks source status only (not destination). Receive requires neither — an already-dispatched transfer can always be completed into a now-inactive destination as a historical-completion/recovery path. Source deactivation after dispatch never invalidates the historical transfer.

## Consequences
- **Positive**: closes a confirmed live oversell defect; makes transfer creation atomic and idempotent for the first time; gives `incoming` real, tested semantics; closes a previously-total deactivation-enforcement gap.
- **Negative**: `receive()`'s signature grows to accept a disposition breakdown (good/damaged/quarantine) rather than a single quantity — a behavioral expansion, not just a bug fix, and must be covered by new tests.
