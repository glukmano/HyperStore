# ADR-0136: Plugin Migrations, Dependency Loading, and Update-Atomicity Contract

| Field       | Value                                |
|-------------|---------------------------------------|
| ID          | ADR-0136                              |
| Status      | Accepted                              |
| Date        | 2026-09-04                            |
| Deciders    | Project Lead, Platform Architect      |
| Phase       | PHASE-16                              |

## Context

Every migration in this codebase lives in one flat root `database/migrations/` directory — no module or plugin has ever used a separate, auto-discovered migrations directory, though Laravel's `loadMigrationsFrom()`/`--path=` primitives fully support it unused. Owner Delta #3 requires Composer dependency loading to fail closed rather than silently degrade. Owner Delta #5 requires the update flow to handle "migrations succeed, then atomic code swap fails" without ever falsely reporting a healthy old version while the database reflects the new one.

## Decision

**Migrations**: `plugins/<id>/database/migrations/` is loaded via `loadMigrationsFrom()` in the plugin's own `boot()`, only when enabled. Ownership is the directory boundary itself — no new tracking table. `plugin:uninstall --purge-data` runs `migrate:rollback --path=plugins/<id>/database/migrations` before removing files; plain uninstall leaves data intact.

**Composer dependencies fail closed**: plugin lifecycle never runs `composer install`/`require`. A plugin package must ship its own `vendor/autoload.php`, generated by the plugin author's own build step — the SDK `require_once`s it verbatim rather than reimplementing any part of Composer's autoload resolution. Before `enable`, the plugin's `vendor/composer/installed.json` is parsed and diffed against the platform root's own `vendor/composer/installed.json` and every currently-enabled plugin's — an exact package-name match at a different version is a **hard block on enable**, surfaced with exact package/version diagnostics through `plugin:doctor` and the Control Center. The plugin manifest's declared `namespace` is validated against a reserved-prefix denylist (`App\`, `Modules\`, `Illuminate\`, `Laravel\`); the manifest's `entrypoint` class must fall under that same validated namespace. No PHP-process-level dependency isolation is claimed — the same-process trust boundary is stated plainly in `docs/plugins/security-trust-model.md`.

**Update atomicity**: the previous plugin code directory remains active and untouched while the new package is staged and fully validated. New migrations run against the still-old-code-active schema, and the resulting `migrations` table batch number is recorded to `plugins.last_migration_batch`. Code activation is an atomic filesystem `rename()` swap (old→backup, staged→live), both same-filesystem atomic operations. If the second rename fails: a **scoped** `migrate:rollback --path=... --batch=<last_migration_batch>` is attempted (never a full-history rollback); on success, the backup directory is restored to live and the plugin continues serving the prior version with its prior `manifest_snapshot`. If that scoped rollback itself fails, the plugin fails closed (`status='failed'`, diagnostics preserved, backup directory kept on disk for manual recovery) — the system never reports the old version as healthy while the database reflects the new one.

## Consequences

- This is the first real exercise of Laravel's per-directory migration loading in this codebase; it is standard, well-supported functionality, not a novel mechanism.
- Same-package-different-version collisions between two enabled plugins (or a plugin and root) are structurally prevented from ever loading simultaneously in the same request, rather than producing non-deterministic "first loader wins" behavior.
- An update that partially fails never leaves the system in a state where reported plugin health and actual database schema disagree — verified by dedicated failure-injection tests.
