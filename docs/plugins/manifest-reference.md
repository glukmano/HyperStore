# Manifest Reference

## `plugin.json`

Parsed and validated by `App\Core\Plugin\DTOs\PluginManifest::fromArray()` —
**every** read of a manifest (install, update, enable, `plugin:doctor`, kernel
discovery) goes through this same validation, so these rules apply uniformly
everywhere, not just at install time.

```json
{
  "manifest_version": 1,
  "id": "acme-example-plugin",
  "name": "Acme Example Plugin",
  "version": "1.2.0",
  "author": "Acme Inc.",
  "license": "MIT",
  "description": "Optional free-text description.",
  "compatibility": { "platform": "^1.0", "php": "^8.4" },
  "dependencies": { "some-other-plugin-id": "^1.0" },
  "requested_permissions": ["plugin.acme-example-plugin.view", "plugin.acme-example-plugin.manage"],
  "capabilities": ["control_center_navigation", "scheduled_tasks"],
  "entrypoint": "Plugins\\AcmeExamplePlugin\\AcmeExamplePluginServiceProvider",
  "namespace": "Plugins\\AcmeExamplePlugin",
  "migrations": "database/migrations",
  "settings_schema": { "api_key": { "secret": true }, "display_name": { "secret": false } }
}
```

### Field reference

| Field | Required | Rules |
|---|---|---|
| `manifest_version` | yes | Must equal `1` (`PluginManifest::SUPPORTED_MANIFEST_VERSION`). Any other value is rejected. |
| `id` | yes | Lowercase slug: `^[a-z0-9]+(-[a-z0-9]+)*$`. No path separators, no `..`. Must exactly match the plugin's directory name. Globally unique — enforced by a real, non-nullable PostgreSQL `UNIQUE` constraint on `plugins.plugin_id` (`uq_plugins_plugin_id`), not just filesystem convention. |
| `name` | yes | Free text. |
| `version` | yes | Free text, checked with `composer/semver` where used as a constraint elsewhere. |
| `author` | yes | Free text. |
| `license` | yes | Free text (an SPDX identifier is recommended but not enforced). |
| `description` | no | Free text, nullable. |
| `compatibility.platform` | no | Semver constraint (via `Composer\Semver\Semver::satisfies()`) checked against `config('plugins.platform_version')`. Defaults to `*` (any). |
| `compatibility.php` | no | Semver constraint checked against `PHP_VERSION`. Defaults to `*`. |
| `dependencies` | no | Map of `plugin-id => semver constraint`. Resolved by `PluginRegistry`'s own Kahn's-algorithm topological sort at every boot cycle, computed from each dependency's stored `manifest_snapshot` — a missing dependency or a cycle blocks `enable`/boot with a diagnostic. |
| `requested_permissions` | no | List of RBAC permission strings. **Must** each be prefixed `plugin.<id>.` (e.g. `plugin.acme-example-plugin.manage`) — any other prefix is a hard validation error. Seeded via the existing `Permission::firstOrCreate()` pattern on `enable`. |
| `capabilities` | no | List of free-text technical capability tags the plugin is requesting (e.g. `control_center_navigation`, `scheduled_tasks`, `outbound_webhooks`, `migrations`). Displayed to the admin and must be explicitly approved before `enable`; a version update that adds a **new** capability not previously granted requires re-approval (diffed against `plugins.granted_permissions`). |
| `entrypoint` | yes | Fully-qualified class name of the plugin's `PluginServiceProvider` subclass. **Must** start with the plugin's own declared `namespace` — an entrypoint outside the plugin's namespace is rejected. |
| `namespace` | yes | The plugin's own PSR-4 namespace root, registered against the plugin's own `vendor/autoload.php`. **Must not** start with any of the reserved platform prefixes: `App\`, `Modules\`, `Illuminate\`, `Laravel\` (`PluginManifest::RESERVED_NAMESPACE_PREFIXES`). |
| `migrations` | no | Relative path (from the plugin root) to its migrations directory. Defaults to `database/migrations`. |
| `settings_schema` | no | Map of setting key → `{ "secret": bool }`. A key marked `secret: true` signals that a plugin's own domain code should store that value encrypted (see the `Crypt::encryptString()` precedent in the developer guide) — the Plugin SDK itself does not persist plugin settings, since enablement is platform-level only (Owner Delta #1) and there is no `plugin_enablements` settings table in this phase. |

### Reserved namespaces and entrypoint ownership (Owner Delta #3)

A plugin's `namespace` may never claim `App\`, `Modules\`, `Illuminate\`, or
`Laravel\` — this is checked on every manifest parse, not just at install.
Its `entrypoint` class must belong to that same declared namespace. This
closes the gap where a malicious or careless plugin package could point its
entrypoint at (or shadow) a platform or framework class.

### Composer dependency loading (Owner Delta #3)

The plugin lifecycle **never** runs `composer install`/`composer require` as
a side effect of any operation. A plugin ships its own pre-built
`vendor/autoload.php`, generated by the plugin author's own build step before
packaging, and it is loaded via a plain `require_once` — never a partial,
hand-rolled reimplementation of Composer's autoload resolution. Before
`enable`, `PluginComposerDependencyChecker` inspects the candidate plugin's
real `vendor/composer/installed.json` (Composer's own genuine manifest of
what it actually installed) and diffs installed package versions against
every other currently-enabled plugin's `installed.json`. A same-package,
incompatible-version collision between two plugins that would both be enabled
is a **hard block on `enable`** — never downgraded to a warning. Diagnostics
are surfaced via `plugin:doctor` and the Control Center detail screen. No
claim of PHP-level dependency isolation is made anywhere: two enabled
plugins' bundled `vendor/` directories share the same PHP process and
autoloader namespace resolution order, exactly like any two Composer
packages would.

## `plugin.sig` — the package signature contract

Optional per package (see [security-trust-model.md](security-trust-model.md)
for the trust-tier and rejection policy this file drives), but when present
it must have this exact shape:

```json
{
  "plugin_id": "acme-example-plugin",
  "version": "1.2.0",
  "manifest_sha256": "<sha256 hex of plugin.json's exact bytes>",
  "files": {
    "composer.json": "<sha256 hex>",
    "plugin.json": "<sha256 hex>",
    "src/AcmeExamplePluginServiceProvider.php": "<sha256 hex>",
    "vendor/autoload.php": "<sha256 hex>"
  },
  "signature_algorithm": "ed25519",
  "publisher_key_id": "acme-2026-01",
  "signature": "<base64 Ed25519 detached signature>"
}
```

### The canonical payload (non-circular, ADR-0134)

The bytes that are actually signed are **not** the raw `plugin.sig` file.
They are computed from `PluginPackageIntegrity::canonicalPayloadBytes()`:

```php
json_encode(
    ['plugin_id' => ..., 'version' => ..., 'manifest_sha256' => ..., 'files' => $filesSortedByKsort],
    JSON_UNESCAPED_SLASHES
)
```

Deterministic properties, each load-bearing and each covered by a unit test
in `tests/Unit/Plugin/PluginSignatureVerifierTest.php`:

- **`files` is always key-sorted** (`ksort()`) before encoding — the same
  file set produces byte-identical canonical payloads regardless of the
  order files were added to the archive.
- **The `signature` field itself is never part of the signed payload** — it
  cannot be, structurally: `canonicalPayloadBytes()` only ever reads
  `plugin_id`, `version`, `manifest_sha256`, and `files`. This is what makes
  the contract non-circular.
- **`signature_algorithm` and `publisher_key_id` are metadata about the
  signature, not signed data** — they select which key to verify against,
  but tampering with them (e.g. claiming a different publisher) still fails
  verification, since the attacker does not hold that publisher's private
  key.

### Verification (`PluginSignatureVerifier`)

Uses PHP 8.4's built-in libsodium: `sodium_crypto_sign_verify_detached()`
against `config('plugins.trusted_publishers')` — an admin-managed map of
`publisher_key_id => base64 Ed25519 public key`. No certificate authority, no
marketplace. `trustLevelForKeyId()` maps a verifying key to
`config('plugins.publisher_trust_tiers')` (`official` or
`verified_third_party`; an unlisted-but-verifying key defaults to
`verified_third_party`). A key not present in `trusted_publishers` at all
never verifies, regardless of tier configuration.

### File-list verification during extraction (`PluginZipInstaller`)

During the byte-counted streaming extraction (see
[security-trust-model.md](security-trust-model.md)), every extracted file's
**actual extracted bytes** are SHA-256 hashed (never ZIP central-directory
metadata) and the resulting map is compared against `plugin.sig`'s `files`
map with `verifyFileListAgainstIntegrity()`:

- **Extra files not listed in `plugin.sig`** → hard rejection
  (`Archive contains files not listed in plugin.sig`). An attacker cannot
  smuggle an additional unverified file into an otherwise validly-signed
  package — every file that ends up on disk must have been part of what was
  signed.
- **Files listed but missing from the archive** → hard rejection
  (`plugin.sig lists files missing from the archive`).
- **A hash mismatch on any listed file** → hard rejection
  (`does not match its signed hash`) — this is what catches tampering with
  file content after signing.

Note that `plugin.json` itself **is** part of the signed file list (its
bytes are hashed into `files['plugin.json']` exactly like any other file),
in addition to `manifest_sha256` being checked independently as an early
fast-fail before full extraction begins.

### Trust policy summary

| Condition | Outcome |
|---|---|
| No `plugin.sig` present | `trust_level = unverified`, allowed only if `config('plugins.allow_unsigned')` is `true` (default: `true` in local/testing, `false` in production) |
| `plugin.sig` present, signature verifies against a trusted key | `trust_level` = that key's configured tier (`official` / `verified_third_party`) |
| `plugin.sig` present, signature does **not** verify | Hard rejection, **always** — regardless of `allow_unsigned`. A present-but-invalid signature is a stronger tamper signal than no signature at all and is never silently downgraded to "unverified and allowed." |
