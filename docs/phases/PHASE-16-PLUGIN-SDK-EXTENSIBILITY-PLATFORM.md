## 1. Objective

Build the architectural foundation for a first-party Plugin SDK (`app/Core/Plugin/`) completing ADR-0006's declared-but-unimplemented Plugin boundary, allowing future first-party and third-party extensions to add capabilities without editing Core source, while preserving Modular Monolith boundaries, tenant isolation, security, deterministic lifecycle, explicit permissions, error isolation, and testability.

## 2. Owner Delta (2026-09-04) — applied corrections to the frozen plan

1. **Plugin enablement is platform-level only.** Installation and runtime enable/disable are platform-level operations. No tenant/store-scoped plugin runtime enablement is built — a plugin registered into a shared, per-request-rebuilt registry (ProductType/PaymentGateway/Carrier/ShippingMethodType/Theme/Navigation) is visible globally the moment its ServiceProvider boots, so contextual runtime filtering at that layer would be structurally incoherent. The `plugin_enablements` table from the frozen plan is **removed** — a single `plugins` table carries all lifecycle state. Tenant/store-scoped business settings, where a plugin's own domain logic needs them, are the plugin's own concern (its own tables), not Plugin Core's. Tenant/store entitlements belong to a future Licensing/SaaS/Feature-Flags phase.
2. **No nullable-column uniqueness.** With `plugin_enablements` removed, the only uniqueness needed is `plugins.plugin_id` (non-nullable, real `UNIQUE`) — no partial index is required.
3. **Composer dependency loading fails closed.** Plugin lifecycle never runs `composer install`/`require`. A plugin package ships its own pre-built `vendor/autoload.php` (generated by the plugin author's own build step), loaded verbatim via `require_once` — no partial hand-rolled Composer-autoload reimplementation. Before `enable`, the plugin's `vendor/composer/installed.json` is inspected and diffed against the platform root's own `vendor/composer/installed.json` and every other enabled plugin's; an exact package-name-with-different-version collision **hard-blocks** `enable` (never a warning). The plugin's manifest `namespace` is validated against a reserved-prefix denylist (`App\`, `Modules\`, `Illuminate\`, `Laravel\`) and the manifest `entrypoint` class must fall under that same validated namespace.
4. **Non-circular package integrity/signature contract**, frozen precisely (§13 below) — a canonical, deterministic payload (sorted per-file SHA-256 map + manifest hash) that excludes the signature itself, verified against **actual extracted bytes**, never ZIP metadata; any archive entry absent from the signed file list (or vice versa) is rejected; invalid signature is always a hard rejection; missing signature follows configured trust policy.
5. **Update atomicity covers the migrate-succeeds/code-swap-fails case** (§11 below): previous plugin code is preserved until the new package is fully validated; the exact migration batch introduced by an update is tracked (`plugins.last_migration_batch`) so a failed code swap can trigger a *scoped* rollback of only that batch; if scoped rollback also fails, the plugin fails closed (`status='failed'`) rather than falsely reporting the old version as healthy.

One additive migration, one table:

```sql
CREATE TABLE plugins (
    id BIGSERIAL PRIMARY KEY,
    plugin_id VARCHAR(150) NOT NULL,
    name VARCHAR(255) NOT NULL,
    version VARCHAR(50) NOT NULL,
    status VARCHAR(30) NOT NULL DEFAULT 'discovered',
    trust_level VARCHAR(30) NOT NULL DEFAULT 'unverified',
    manifest_snapshot JSONB NOT NULL,
    granted_permissions JSONB NULL,
    permissions_approved_at TIMESTAMP NULL,
    consecutive_boot_failures INTEGER NOT NULL DEFAULT 0,
    last_migration_batch INTEGER NULL,
    failure_reason TEXT NULL,
    installed_at TIMESTAMP NULL,
    enabled_at TIMESTAMP NULL,
    disabled_at TIMESTAMP NULL,
    created_at TIMESTAMP NOT NULL DEFAULT now(),
    updated_at TIMESTAMP NOT NULL DEFAULT now(),
    CONSTRAINT uq_plugins_plugin_id UNIQUE (plugin_id)
);
```

No other new tables. No nullable-column uniqueness anywhere.

## 11. Update Atomicity Protocol (Owner Delta #5, frozen)

1. Old plugin code at `plugins/<id>/` remains untouched and active throughout.
2. New package is fully staged and validated in isolation (same pipeline as fresh install).
3. New migrations run against the still-old-code-active database; the resulting Laravel `migrations` table batch number is recorded to `plugins.last_migration_batch`.
4. Atomic code swap: `rename(plugins/<id>/, plugins/<id>.rollback-<ts>/)` then `rename(staged/, plugins/<id>/)` — both are atomic renames on the same filesystem.
5. **If the second rename fails**: attempt `migrate:rollback --path=... --batch=<last_migration_batch>` (scoped to exactly this update's migrations, never the plugin's full history). If that succeeds, restore old code via `rename(plugins/<id>.rollback-<ts>/, plugins/<id>/)`, keep `manifest_snapshot`/`version` at the OLD value, plugin remains `enabled` and functioning on the prior version.
6. **If the scoped rollback itself fails**: fail closed — `status='failed'`, `failure_reason` persisted, the plugin is treated as broken (never re-enabled automatically); the old code backup directory is preserved on disk (not deleted) for manual recovery; the system never reports the old version as "healthy" while the DB schema reflects the new version.
7. Only after a successful code swap is `manifest_snapshot`/`version`/`trust_level` published as the new active values, and only then does the update's own `AuditManagerInterface` entry record success.

## 12. Security

Same-process trust boundary stated plainly (no sandboxing claim). Byte-counted streaming ZIP extraction (§13). Reserved-namespace validation. Composer dependency hard-block on collision. Secrets (where a plugin needs them, via its own tables) never appear in Livewire state/logs/audit payloads. Tenant isolation is unaffected since Plugin Core itself carries no tenant-scoped state (Owner Delta #1).

## 13. Package Integrity / Signature Contract (frozen, non-circular)

**Format**: "HyperStore Plugin Package v1". A package is a `.zip` containing `plugin.json` (manifest, no integrity fields inside it) and, optionally, a sibling `plugin.sig` file.

**Canonical payload** (built by the plugin author's packaging tool, verified by the SDK):
```
payload = {
  "plugin_id": <manifest id>,
  "version": <manifest version>,
  "manifest_sha256": sha256(plugin.json bytes),
  "files": { <relative_path>: sha256(actual file bytes), ... }   // every non-plugin.sig file in the archive, keys sorted ascending
}
```
Serialized as `json_encode($payload, JSON_UNESCAPED_SLASHES)` with recursively `ksort()`-ed keys — one deterministic byte sequence.

`plugin.sig` contents: the canonical payload's fields plus `signature_algorithm` (`ed25519`), `publisher_key_id`, and `signature` (base64 `sodium_crypto_sign_detached($canonicalPayloadBytes, $publisherSecretKey)`) — **the signature key is never part of the signed bytes**.

**Verification** (during the same streaming extraction pass, not a separate step): every extracted file's actual decompressed bytes are hashed and compared against `files[path]`; any archive entry absent from `files{}`, or any `files{}` key absent from the archive, rejects the whole package (closes the "extra/unlisted file bypasses verification" hole). `manifest_sha256` is computed from the actually-extracted `plugin.json` bytes, never a declared/ZIP-metadata value. Signature verified via `sodium_crypto_sign_verify_detached()` against every key in `config('plugins.trusted_publishers')`.

**Trust outcome**: no `plugin.sig` → `unverified` tier, allowed only if `config('plugins.allow_unsigned')` (default true local/testing, false production). `plugin.sig` present and valid against a known key → tier matches that key's configured tier (`official`/`verified_third_party`). `plugin.sig` present but invalid against every configured key → **hard install rejection**, unconditionally, regardless of `allow_unsigned`.
